01 / SOAP

SOAP: chuẩn hóa cấu trúc thông điệp

Phù hợp khi tích hợp cần tuân thủ hợp đồng và hệ sinh thái SOAP có sẵn.

<env:Envelope
 xmlns:env="http://www.w3.org/2003/05/soap-envelope"
 xmlns:s="urn:student-management">
  <env:Body>
    <s:GetStudentRequest>
      <s:studentCode>SE181234</s:studentCode>
    </s:GetStudentRequest>
  </env:Body>
</env:Envelope>

Cơ chế

XML request → SOAP node xử lý → logic nghiệp vụ → Body kết quả hoặc Fault.

Ưu điểm / giới hạn

Công cụ hợp đồng và liên thông tốt; cần xử lý XML, namespace và cấu hình tích hợp.

WSDL thường dùng, không bắt buộc bởi SOAP core. WS-Security là phần mở rộng, không tự có trong mọi message.

Cơ sở kỹ thuật: [1] [13]
Ghi chú thuyết trình: Header là tùy chọn; Body là bắt buộc. SOAP không mặc nhiên có chữ ký số hoặc giao dịch phân tán.

01 / REST

REST: tài nguyên và giao diện đồng nhất

Ví dụ HTTP: GET /api/v1/students/SE181234 trả một biểu diễn của sinh viên.

Client–server & stateless

Tách giao diện khỏi dữ liệu. Request mang đủ ngữ cảnh xử lý; server vẫn lưu được dữ liệu nghiệp vụ.

Cacheable & layered system

Khai báo khả năng cache. Có thể đặt gateway giữa client và API mà không lộ cấu trúc bên trong.

Uniform interface

Định danh tài nguyên; thao tác qua biểu diễn; thông điệp tự mô tả; hypermedia dẫn hướng bước tiếp theo.

Code-on-demand · tùy chọn

Server có thể gửi mã thực thi cho client. Đây không phải ràng buộc bắt buộc.

Trả JSON qua HTTP chưa đủ để là REST. Demo dùng HTTP theo hướng REST và minh họa liên kết; không tuyên bố hiện thực đầy đủ mọi ràng buộc.

Cơ sở kỹ thuật: [2]
Ghi chú thuyết trình: Stateless không có nghĩa không dùng database. JWT không phải yêu cầu bắt buộc của REST.

01 / GRAPHQL & gRPC

Chủ động về dữ liệu hoặc về phương thức

GraphQL tập trung vào dữ liệu client cần; gRPC tập trung vào hợp đồng dịch vụ.

GraphQL

  • Schema xác định kiểu và trường hợp lệ.
  • query đọc; mutation thay đổi; subscription nhận sự kiện.
  • Thường dùng HTTP và một endpoint.
  • Cần kiểm soát phân quyền, query cost và N+1.

Đánh đổi: client linh hoạt hơn, server quản lý truy vấn phức tạp hơn.

gRPC

  • Native gRPC sử dụng HTTP/2.
  • Protobuf là lựa chọn mặc định.
  • Unary, server streaming, client streaming, bidirectional streaming.
  • Browser thường cần gRPC-Web/lớp tương thích.

Đánh đổi: sinh mã tiện lợi nhưng cần toolchain và quản lý tương thích.

Cơ sở kỹ thuật: [3] [5] [6] [7]
Ghi chú thuyết trình: GraphQL bắt buộc có schema nhưng không bắt buộc viết file SDL thủ công. gRPC-Web không có mọi khả năng streaming của native gRPC.

02 / ĐỐI CHIẾU

Cùng đọc một sinh viên: GraphQL và gRPC

GraphQL chọn trường; gRPC gửi request theo message đã định nghĩa.

GraphQL · schema, query, response

type Student { studentCode: ID!, fullName: String! }
type Query { student(code: ID!): Student }

query {
  student(code: "SE181234") {
    studentCode
    fullName
  }
}

{"data":{"student":{
  "studentCode":"SE181234",
  "fullName":"Nguyễn Văn An"
}}}

gRPC · hợp đồng student.proto

syntax = "proto3";
package sms.v1;
service StudentService {
  rpc GetStudent(GetStudentRequest) returns (Student);
}
message GetStudentRequest {
  string student_code = 1;
}
message Student {
  string student_code = 1;
  string full_name = 2;
}

Stub gọi GetStudent với student_code = SE181234 và nhận Student tương ứng. .proto là hợp đồng, không phải payload nhị phân trên dây.

03 / BỐI CẢNH

Hệ thống được chọn: quản lý sinh viên

Giả định thiết kế cho Assignment; không phải số liệu vận hành của một trường.

Người dùng

Sinh viên tra hồ sơ; giảng viên nhập điểm; phòng đào tạo quản lý sinh viên và môn học.

Nghiệp vụ

CRUD hồ sơ, môn học, đăng ký học; tra cứu kết quả. Tài nguyên có định danh và quan hệ rõ ràng.

Client & đội phát triển

Web là client chính, có thể thêm mobile. Đội nhỏ quen HTTP/JSON và ASP.NET Core.

Ràng buộc

Giả định 10.000 sinh viên. Không có đối tác bắt buộc SOAP; chưa cần streaming hai chiều hoặc microservices.

Ưu tiên: tích hợp browser → triển khai/bàn giao thuận tiện → kiểm soát truy cập → mở rộng theo tải đo được.

Ghi chú thuyết trình: Số người dùng không tự suy ra requests/giây. Phải đo concurrency, workload và giới hạn database.

03 / QUYẾT ĐỊNH

Chọn REST API cho giao tiếp của hệ thống

REST đáp ứng các ưu tiên đã nêu với ít thành phần bổ sung cho client web.

01 · Khớp nghiệp vụ

/students, /courses, /enrollments là tài nguyên rõ ràng; dùng phương thức HTTP nhất quán.

02 · Dễ tích hợp

Browser sử dụng fetch; mô tả hợp đồng bằng OpenAPI; thử và gỡ lỗi bằng HTTP client.

03 · Chi phí phù hợp

Bắt đầu với một backend phân lớp; chưa cần gateway GraphQL hoặc lớp chuyển đổi gRPC-Web.

04 · Vận hành có cơ sở

Stateless hỗ trợ nhân bản API; cache cho danh mục công khai. Dữ liệu riêng tư có chính sách riêng.

Quyết định theo tình huống, không phải kết luận REST tốt hơn trong mọi hệ thống.

04 / REQUEST / RESPONSE

GET: đọc hồ sơ sinh viên

Host và token chỉ là ký hiệu minh họa, không phải dịch vụ đang hoạt động.

Client → Request

GET /api/v1/students/SE181234 HTTP/1.1
Host: sms.example.edu
Authorization: Bearer <access_token>
Accept: application/json

API xử lý

Xác thực → quyền sở hữu → đọc dữ liệu → ánh xạ DTO → JSON.

GET an toàn và lũy đẳng theo ngữ nghĩa HTTP: không yêu cầu thay đổi trạng thái nghiệp vụ.

API → Response

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

  "major": "Software Engineering",
  "status": "ACTIVE",
  "_links": {

04 / LỖI & CACHE

Phản hồi rõ ràng; cache đúng dữ liệu

Status diễn đạt loại kết quả; body bổ sung ngữ cảnh cho client.

HTTP/1.1 404 Not Found
Content-Type: application/problem+json
Cache-Control: no-store

{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "Không tìm thấy sinh viên.",
  "instance": "/api/v1/students/SE999999"
}

Problem Details theo RFC 9457. Không trả stack trace hay thông tin nhạy cảm.

Chính sách cho case study

  • Hồ sơ/điểm cá nhân: no-store trong ví dụ.
  • Danh mục thực sự công khai: có thể public, max-age=300 nếu chấp nhận trễ 5 phút.
  • ETag + If-None-Match: khớp → 304, không body.
  • ETag không thay thế phân quyền. Không cache chung dữ liệu theo người dùng.

401 cần WWW-Authenticate; 403 là từ chối quyền truy cập.

05 / BẢO VỆ QUYẾT ĐỊNH
Hiệu năng phải đo; kết luận có điều kiện
Không xếp hạng tốc độ tuyệt đối hoặc đưa benchmark thiếu bối cảnh.
Đo như thế nào?
Cùng nghiệp vụ, dữ liệu, phần cứng và mạng. Ghi rõ cache, nén, TLS, concurrency và warm-up.
Theo dõi những gì?
Độ trễ p50/p95/p99, requests/giây, tỷ lệ lỗi, CPU, bộ nhớ và byte truyền. Phân biệt database với serialization.
GraphQL luôn trả 200?
Không. Lỗi thực thi có thể kèm data và 200; lỗi request/HTTP có thể trả 4xx/5xx tùy tình huống, media type.
gRPC luôn nhanh và an toàn?
Không. Phụ thuộc workload; TLS/mTLS phải cấu hình. HTTP/2 vẫn chịu ảnh hưởng mất gói ở tầng TCP.
Kết luận: REST phù hợp với web + CRUD + đội nhỏ trong giả định bài. Ba lựa chọn còn lại có lợi thế khi ràng buộc khác xuất hiện.

07 / THÍ NGHIỆM THỰC TẾ
Thiết kế: gRPC có nhanh hơn REST?
Giả thuyết được kiểm chứng bằng backend thật; HTTP/2 cho cả hai.
Cùng nghiệp vụ
Đọc 1, 100 hoặc 1.000 sinh viên: mã, tên, ngành. REST trả JSON; gRPC trả Protobuf. Cùng nguồn dữ liệu trong RAM.
Cùng truyền tải
HTTP/2 cho cả hai; tái sử dụng kết nối. Không TLS, database, nén hoặc cache response. Hai process cùng máy.
36 lượt đo thực tế
Đồng thời 1 / 32; mỗi cấu hình lặp 3 lần. Mỗi lượt: 2 giây warm-up + 5 giây đo. Đảo thứ tự REST/gRPC giữa các lần.
Kiểm tra dữ liệu
Client decode và so sánh mọi trường/bản ghi. Đo latency, req/s thành công, lỗi và CPU; không tạo số giả trong browser.
Pilot: Ryzen 7 7735HS · 16 luồng · Windows · .NET 10 Release · loopback. Chưa đại diện mạng thật hoặc production.
Ghi chú thuyết trình: Lượt chạy này là pilot. Bản README cung cấp ma trận chạy lâu hơn để tăng độ tin cậy.

07 / GIẢI THÍCH
Kích thước dữ liệu làm thay đổi kết quả
Thông lượng, latency và payload cần được đọc cùng nhau.
Payload nhỏ · 1 SV / 32 đồng thời
REST có thông lượng cao hơn 1.56 lần. Không được giả định gRPC thắng chỉ vì dùng nhị phân.
Payload lớn · 1.000 SV / 32 đồng thời
gRPC có thông lượng cao hơn 1.74 lần. p95 REST 11.316 ms; gRPC 7.185 ms.
Giải thích có điều kiện
1.000 SV: JSON 84,014 byte, Protobuf 48,000 byte. Payload nhỏ hơn có thể giúp; chưa cô lập tác động serializer.
Giới hạn kết luận
Client/server chung máy; lượt đo ngắn; không TLS/database. Mapping, JIT, GC và tải nền đều có thể ảnh hưởng.
REST vẫn phù hợp case study web + CRUD. Muốn kết luận cho production: đo dài hơn, tách máy, bật TLS và kiểm tra tải thực.
